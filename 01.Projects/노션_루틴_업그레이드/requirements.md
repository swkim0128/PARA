## 0. 공통 아키텍처 원칙 (2026-08-02 접수)

- 이 3종은 **개인 관리 기능(도메인)** 이며, 노션은 현재 선택된 **저장소(백엔드)일 뿐** 기능의 정체성이 아니다.
- **나중에 노션 없이도 관리가 진행될 수 있어야 한다** — 저장소 교체 가능성을 전제로 설계한다.
- 설계 지침:
    - **도메인 규칙과 저장소 접근을 분리**한다. 도메인 규칙(슬롯 시각 매핑, 예산 카테고리, KPT 템플릿, wish list 매핑 규칙, 재고 이월 규칙 등)은 저장소 중립 문서로 정의하고, 노션 MCP 호출 절차는 어댑터 계층으로 격리한다.
    - 신규 기능(wish list, 뱅크샐러드 import, 요일×끼니 식단 등)은 처음부터 이 분리 구조로 설계한다.
    - 스킬 명명(`notion-*`)·구조 재편은 Phase 3 설계 시 결정한다 (지금 강제 리네이밍하지 않음 — Phase 1은 현행 구조 안정화가 목적).

### 스킬 계층 구조 (2026-08-02 추가 접수)

- 3종 관리 기능은 **스킬로 수행하는 것이 맞다.** 단, 구조는 아래 중 설계 단계에서 선택한다:
    - **(a) 기능별 복수 스킬** — 한 관리 기능을 여러 스킬이 분담
    - **(b) 단일 스킬 + 케이스별 조치사항 내장** — 하나의 스킬 아래 여러 경우(입력 유형·상황)에 대한 처리 절차를 모두 포함
    - **(c) 매핑 레지스트리(라우터)** — 관리 기능 → 사용할 스킬/MCP 를 매핑하는 층을 만들어, 요청이 오면 매핑을 보고 올바른 스킬·MCP로 라우팅
- **환경 이식성(필수)**: 위 개인관리 기능들은 **어떤 환경에서든 사용 가능해야 한다** — 특정 툴(Claude Code)이나 특정 MCP 가용성에 종속되지 않고, 환경별 가용 수단(스킬/MCP/SOP 폴백)으로 동일 기능을 수행할 수 있어야 한다.

### 명명·배포 원칙 (2026-08-02 추가 접수)

- **도메인 우선 명명**: Claude Code 플러그인을 포함한 모든 자산(플러그인·스킬·명령)의 제목은 **목적 도메인(개인관리)** 기준으로 짓는다 — 도구/저장소 이름(노션)이 제목이 되면 안 된다. 기존 노션 명명 자산은 존재 여부를 확인하고 도메인 명칭으로 개명한다.
- **전방위 이식성**: 개인관리 기능은 **어느 컴퓨터, 어느 AI 도구, 어느 환경**에서든 사용 가능해야 하며, Claude Code 전용 자산에만 속해서는 안 된다. (충족 구조: 도메인 문서 = para 볼트(git으로 모든 컴에 동기) / 스킬 = `~/.agents/skills` 공용 배포(agy·Claude·Codex·Gemini 공유) / Claude 플러그인 = Claude 전용 얇은 명령 표면일 뿐 기능의 본체가 아님)

## 1. 일정관리 (2026-08-02 접수)

### 사용 도구
- **노션 MCP + 구글 캘린더 MCP** 두 가지를 사용해 일정관리를 수행한다.

### Week List (노션 일지 페이지 첫 섹션)
- 이번 주에 **해야 하는 일 혹은 했던 일**들을 목차로 기록한다.
- 내용은 **업무 / 개인 일정**으로 나누어, 각 항목을 해당 분류에 포함시킨다.

### Week Things (요일별 섹션)
- **일~토** 각 요일에 했던 일이나 예정인 일을 등록한다.
- **각 시간 블럭별로** 해당 시간대에 했던 일을 기록한다.
- **작업 예정인 일은 미리 등록**한다 (사후 기록만이 아니라 사전 계획 등록).

### 주간 회고
- **매주 일요일**, 이번 주에 기록한 일들을 바탕으로 회고를 작성한다.
- 회고는 회고 템플릿을 사용하며, 템플릿은 **KPT**(Keep·Problem·Try)를 사용한다.

### 요구사항 ↔ 현재 구현 갭 분석

| # | 요구 | 현재 상태 | 갭 |
|---|---|---|---|
| R1 | 노션 MCP + 구글 캘린더 MCP | 노션 MCP ✅ / 캘린더는 `gws` **CLI** 기반(`gws-cal-to-notion`), OAuth 재인증 필요 상태 | **gws CLI → Google Calendar MCP 전환** 필요 |
| R2 | Week List 업무/개인 분류 목차 | WORK/LIFE 2컬럼 + 하위 카테고리 구조 일치 | 없음 (유지) |
| R3 | Week Things 일~토 등록 | 요일별 슬롯 구조 일치 | 없음 (유지) |
| R4 | 시간 블럭별 기록 | 슬롯 시각 매핑 존재하나 스킬 reference에 **주말 시각표 결손** | 시각표를 스킬 정본에 반영 (diagnosis #9) |
| R5 | 작업 예정 미리 등록 | 등록 자체는 가능하나 **예정/완료 상태 구분 표기 규칙 없음** | 표기 규칙 신설 필요 |
| R6 | 일요일 KPT 회고 | `notion-weekly-retrospective`가 KPT 템플릿 구현 ✅, 단 훅은 **안내만** 하고 실행은 수동 | **일요일 자동(또는 반자동) 실행 루틴** 필요 |

## 2. 예산관리 (2026-08-02 접수)

### Wish List
- **구입 예정이거나 원하는 품목**을 wish list로 미리 등록한다.

### 지출 기록
- **뱅크샐러드에서 다운받은 가계부 데이터**를 기준으로 지출 내역을 기록한다.

### Wish List 매핑
- 지출 내역을 기준으로, 미리 입력한 **wish list 품목과 매핑하거나 대체** 처리한다.

### 월말 정리
- **매월 말**, 그 달의 지출 내용을 정리·요약해 해당 월 예산 페이지의 **컨텐트 부분에 기록**한다.

### 요구사항 ↔ 현재 구현 갭 분석

| # | 요구 | 현재 상태 | 갭 |
|---|---|---|---|
| B1 | Wish list 등록 | 없음 | **신규.** 월 예산 페이지 내 섹션 vs 별도 DB — 구조 설계 필요 |
| B2 | 뱅크샐러드 데이터 기준 지출 기록 | 대화 입력 기반("오늘 N원 썼어") 수동 기록만 | **신규.** 내보내기 파일(xlsx) 파싱 → 일괄 기록 파이프라인. 재업로드 시 **중복 방지 키** 설계 필요 |
| B3 | 지출 ↔ wish list 매핑/대체 | 없음 | **신규.** 지출과 품목 매칭 → 구매완료 처리, 불일치 시 대체 품목 처리 규칙 필요 |
| B4 | 월말 지출 정리·요약 | 카테고리별 합계 표는 상시 갱신하나 월말 요약 루틴 없음 | **신규.** 월말 실행 루틴 + 요약 템플릿 |

> **설계 확정 (2026-08-02 사용자 답변)**: ① 뱅크샐러드 파일은 **고정 드롭 폴더**로 수령 ② 대화 입력 병행은 유지(기본값 채택) ③ "대체" = **유사 품목 구매 시 wish list 항목을 실구매 품목으로 교체하고 구매완료 처리**.

## 3. 식단관리 (2026-08-02 접수)

### 보유 식재료 관리
- **현재 가지고 있는 식재료**를 관리한다 (재고 개념).

### 식사 기록·계획
- 이번 주 **점심·저녁**에 **뭘 먹었는지**(실적), **뭘 먹을 예정인지**(계획)를 기록한다.

### 요구사항 ↔ 현재 구현 갭 분석

| # | 요구 | 현재 상태 | 갭 |
|---|---|---|---|
| D1 | 보유 식재료 관리 | 주간 Diet 페이지의 Ingredients relation 추가/제거 지원 | **부분 갭.** 재고의 SoT가 주간 페이지 relation이라 주 전환 시 이월 규칙이 불명확 — "현재 보유" 관점의 관리 규칙 명확화 필요 |
| D2 | 점심·저녁별 먹은 것/먹을 예정 기록 | Foods relation append(먹은 음식)만 — **요일·끼니 구분 없음**, 예정(식단 계획) 개념 없음 | **신규.** 요일×끼니(점심/저녁) 구조 + 실적/예정 구분 설계 필요 |

> **설계 확정 (2026-08-02 사용자 답변)**: ① 재고 SoT = **Ingredients 마스터의 재고 상태 속성** (주간 페이지 relation은 파생 뷰) ② 요일×끼니 기록 = **Diet 페이지 본문 표**.
