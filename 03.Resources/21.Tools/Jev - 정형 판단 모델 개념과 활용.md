# Jev — 정형 판단 모델 개념과 활용

조사일: 2026-09-19. 공식 문서 재확인 기준이며, 공급자 설명과 로컬 테스트 결과를 구분한다.

관련 계획: [[archify-jev-도입계획-20260919]]

## 1. 핵심 개념

Jev는 TypeSafe의 첫 System One 모델이다. 자연어를 이해하고, 개발자가 지정한 답의 범위 안에서 판단값과 확률을 반환한다. 입력은 자연어 문자열이나 JSON 객체·배열일 수 있으므로, 입력부터 모두 정형 데이터여야 하는 것은 아니다. 응답 작성·코드 생성·판단 근거의 자유서술은 담당하지 않는다. [공식 개념](https://docs.typesafe.ai/concepts/system-one)

따라서 “LLM 대신 정형화된 데이터를 구성해 작업한다”는 이해는 다음처럼 구체화하면 정확하다.

- 개발자가 판단 대상과 질문·선택 기준을 구성한다.
- Jev가 해당 정보를 평가해 정형 판단값을 반환한다.
- 호출한 프로그램이 판단값에 따라 실제 작업을 실행한다.

Jev가 스스로 터미널 명령을 실행하거나 파일을 수정하는 에이전트라는 의미는 아니다. 공식 예제도 판단 결과를 코드의 조건문과 연결해 작업을 배정한다. [판단과 실행의 연결](https://docs.typesafe.ai/primitives/choice)

## 2. 모델·API·SDK의 구분

- **Jev**: 판단을 수행하는 원격 AI 모델.
- **TypeSafe API**: 모델을 호출하는 서비스 인터페이스.
- **typesafe-sdk**: Python 프로그램이 API를 호출하고 응답 객체를 다루게 하는 클라이언트 라이브러리.

이번에 로컬에 설치한 것은 SDK 0.7.0이다. 모델 가중치를 내려받아 오프라인으로 실행하도록 설치한 것이 아니다. 공식 SDK도 API 키를 설정한 뒤 `TypeSafeClient.system_one()`을 호출한다. [공식 Python SDK](https://github.com/typesafe-ai/typesafe-sdk-python)

## 3. 입력과 반환 유형

호출에는 `state`(판단할 정보), `model`(모델 선택), `questions`(질문 목록)를 전달한다. 질문에는 `instructions`와 답의 기준인 `criteria`를 지정한다. 문서·메시지와 필요한 맥락을 state에 포함하는 방식이다. [State](https://docs.typesafe.ai/concepts/state), [Choice 요청 구조](https://docs.typesafe.ai/primitives/choice)

| 유형 | 질문 예 | 반환 의미 |
|---|---|---|
| Choice | 신규 요청·질문·정보 공유 중 무엇인가? | 선택지 하나, 각 선택지의 확률, confidence |
| Score | 긴급도가 낮음·보통·높음 중 어디에 가까운가? | 단계 번호의 확률 가중 평균, 단계별 확률, confidence |
| Noul | 사용자가 환불을 요청했는가? | 참이라고 판단할 확률 0~1 |

Choice는 최대 255개 선택지를 받는다. Score는 2~10개 단계의 설명을 받으며 결과가 정수일 필요는 없다. Noul은 별도 confidence 없이 `noul` 수치를 반환한다. 코드가 필요에 따라 임계값으로 불리언으로 바꾼다. [Choice](https://docs.typesafe.ai/primitives/choice), [Score](https://docs.typesafe.ai/primitives/score), [Noul](https://docs.typesafe.ai/primitives/noul)

## 4. 예시: 개인 작업 메시지 분류

다음은 이해를 위한 자체 설계 예시이며 실제 모델 호출 결과가 아니다.

```text
state: "주말까지 독서 기록 화면을 만들어 줘."
instructions: "메시지의 의도를 분류하라."
criteria:
  new_task: 새 작업을 요청함
  question: 답변이나 설명을 요청함
  information: 정보만 공유함
  other: 위 분류에 해당하지 않음

Jev가 반환할 수 있는 선택값의 예: new_task
호출 프로그램의 후속 처리 예: 작업 초안 생성
```

처리 흐름은 `메시지 수집 → 질문 구성 → Jev 판단 → 결과·불확실성 확인 → 프로그램의 작업 실행`이다. 모델은 분류를 담당하고, 초안 생성 함수·저장 위치·승인 절차는 프로그램이 정의한다. 이 적용 방식은 공식 문서의 판단 결과를 코드로 연결하는 패턴에서 도출한 설계다. [공식 활용 흐름](https://docs.typesafe.ai/concepts/system-one)

## 5. LLM과 무엇이 다른가

TypeSafe는 사전학습 언어 모델을 정형 판단과 확률 보정에 맞춰 학습하는 RLCD(Reinforcement Learning for Calibrated Decisions)를 설명한다. “AI 모델 없이 JSON 규칙만 실행한다”거나 “언어 모델과 완전히 무관하다”는 해석은 맞지 않는다. 학습 방식에 관한 설명은 공급자 주장으로, 여기서 독립 검증한 것은 아니다. [공식 AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer)

일반 LLM에도 정형 출력을 요구할 수 있다. TypeSafe 역시 비교 실험용 LLM 어댑터를 공개한다. 차이는 JSON 사용 여부만이 아니라 정형 판단·확률 반환을 목표로 설계한 모델이라는 점이다. 성능 우위는 개별 업무 데이터로 검증해야 한다. [공식 출시 글](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

적용 해석: 메시지 분류·라우팅·우선순위 평가처럼 답의 범위를 미리 정할 수 있는 판단을 Jev에 맡기고, 설명문·코드 생성처럼 개방형 출력이 필요한 부분은 LLM에 맡기는 구성을 고려할 수 있다. 전체 에이전트 교체보다는 특정 판단 단계 교체에 해당한다.

## 6. 확률·confidence·정확성

`probabilities`는 후보별 확률이다. Choice와 Score의 `confidence`는 그 확률 분포가 얼마나 한쪽으로 집중되는지 요약한 수치다. 선택된 답의 확률과 같은 값으로 취급하거나, confidence 0.8을 곧바로 정답률 80%로 읽으면 안 된다. [공식 Confidence](https://docs.typesafe.ai/confidence)

확률 보정은 여러 예측을 모았을 때 예측 확률과 관측 결과가 대응하도록 하는 목표다. 개별 답의 정확성을 보증하지 않는다. 출력 타입이 맞아도 분류가 틀릴 수 있다. [공식 AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer)

우리 적용에서는 정답 데이터로 정확도·혼동표를 측정하고, 불확실한 결과를 사람 또는 다른 모델에 넘기는 기준을 정해야 한다. 임계값은 미리 보편값으로 확정하지 않는다. [공식 임계값 지침](https://docs.typesafe.ai/confidence)

## 8. 추가 읽기 — 활용 사례 블로그 검토 (2026-09-19)

검토 대상: [Jev 활용 사례 정리](https://javaexpert.tistory.com/1838) (2026-09-18). 이 글은 공식 문서가 아니라 활용 아이디어를 정리한 2차 출처다.

### 공식 문서와 일치하는 핵심

글의 “Control Flow는 코드가 담당하고 Semantic Decision은 Jev가 담당한다”는 요약은 정확하다. Jev가 반환한 Choice·Score·Noul을 코드의 `if`·`switch`·워크플로우 분기로 연결하는 방식이다. 따라서 Jev는 에이전트를 대체하기보다 에이전트·검색·업무 자동화의 **판단 노드**로 넣는 것이 맞다.

블로그가 제시한 활용을 공식 primitive로 다시 매핑하면 다음과 같다.

| 블로그의 활용 표현 | Jev 질문 유형 | 호출 프로그램의 역할 |
|---|---|---|
| 분류·라우팅·도구 선택·모델 선택 | Choice | 선택값에 따라 함수·도구·후속 모델 호출 |
| 스팸·개인정보·긴급도·정책 위반 탐지 | Noul 또는 Choice | 임계값 이하/이상에서 허용·차단·검토 분기 |
| 관련도·우선순위·품질·후보 정렬 | Score | 점수·확률로 정렬, 상위 후보만 후속 처리 |
| RAG 후보 재정렬 | Choice 또는 Score | 벡터 검색 후보를 먼저 좁힌 후 Jev 결과로 선택 |
| LLM 출력 검사 | Noul·Choice·Score | 불확실하거나 실패한 결과를 재생성·사람 검토로 전달 |

### 우리 환경에 적용할 후보

1. **슬랙 멘션 분류**: 현행 `slack-mention-triage`의 네 분류를 Choice로 판단한다. 이는 계획 C-4의 골든셋 대상과 일치한다.
2. **도구·스킬 후보 제안**: 사용자 요청의 의도를 Choice로 좁힌 뒤, 기존 규칙·스킬 트리거를 적용한다. 실제 실행 권한 판단은 계속 하네스 규칙과 코드가 담당한다.
3. **검증 결과의 검토 필요성 판정**: 테스트·린트 출력이 사람 검토를 필요로 하는지 Noul 또는 Choice로 보조 판단할 수 있다. 정적 검증 자체를 대체하지는 않는다.

### 도입 전에 검증할 제한

- 블로그의 검색·RAG·랭킹·대규모 분석·금융·법률 사례는 **가능한 활용 방향**이며, Jev가 해당 업무에서 정확도·비용·지연시간 우위를 보인다는 독립 증거는 아니다.
- “범용 검증”도 사실성이나 인용 정확성을 보장하지 않는다. Jev의 판단 결과 자체를 골든셋으로 평가하고 confidence 임계값 아래에서는 사람 또는 LLM 검토로 넘겨야 한다.
- 게임·금융·법률·개인정보 사례는 현재 개인 하네스의 도입 범위 밖이다. 특히 업무 데이터의 외부 API 전송은 계획 C-6 정책 게이트를 먼저 통과해야 한다.

이 블로그는 Jev의 적합한 위치를 더 명확히 했다. 즉, 자유 텍스트 생성 대신 **제한된 선택지에서 다음 행동을 결정하는 단계**에 먼저 적용하고, 실제 효과는 개인 비업무 데이터의 30건 골든셋과 지연시간 측정으로 판단한다.

## 9. 추가 읽기 — “글을 쓰지 않는 AI” 블로그 검토 (2026-09-19)

검토 대상: [Jev AI란? 글을 쓰지 않는 AI, TypeSafe System One 모델 완전 정리](https://metime.tistory.com/entry/Jev-AI%EB%9E%80-%EA%B8%80%EC%9D%84-%EC%93%B0%EC%A7%80-%EC%95%8A%EB%8A%94-AI-TypeSafe-System-One-%EB%AA%A8%EB%8D%B8-%EC%99%84%EC%A0%84-%EC%A0%95%EB%A6%AC) (2026-09-19). 브라우저로 본문을 읽었으며, 이 글은 2차 설명 자료다.

### Claude Code·Codex와의 관계

글의 핵심 설명은 공식 문서와 일치한다. Jev는 문장 생성·코드 작성·파일 읽기·도구 호출·명령 실행을 하지 않는다. `state`와 질문을 받아 Choice·Score·Noul 형태의 판단값을 반환할 뿐이다.

따라서 다음처럼 역할이 나뉜다.

```text
사용자 요청 또는 프로그램 상태
        ↓
Jev: 분류·점수·확률 판단
        ↓
Claude Code / Codex / 애플리케이션 코드: 계획·도구 호출·파일 변경·명령 실행
```

Jev를 도입한다고 Claude Code나 Codex를 사용하지 않게 되는 것은 아니다. 반대로 에이전트가 매번 장문 추론으로 처리할 필요가 없는 좁은 판단을 Jev에 맡기고, 실제 작업은 에이전트와 일반 코드가 수행하는 조합이 현실적인 사용 방식이다.

### 새로 보완된 이해

- Jev는 단순 분류기보다 넓게, 한 요청에 여러 독립 판단을 넣어 함께 반환하는 모델로 이해할 수 있다. 예를 들어 멘션 하나에 `분류`, `긴급도`, `사람 검토 필요 여부`를 함께 물을 수 있다. 공식 Choice 문서는 여러 질문을 한 요청으로 보내라고 권장하며, 질문은 병렬 평가된다고 설명한다.
- 입력 `state`는 자연어만이 아니라 JSON 객체·배열도 가능하다. 다만 현재 텍스트 기반 입력만 지원하므로 이미지·음성·동영상의 이해나 직접적인 구조화 데이터 추출 도구로 오해하면 안 된다.
- “응답이 정형이므로 안전하다”는 결론은 성립하지 않는다. 출력 스키마는 맞아도 의미 판단은 틀릴 수 있다. confidence와 골든셋 평가, 실제 실행 전의 코드 규칙이 계속 필요하다.

### 우리 하네스의 최소 적용 형태

현재 가장 작은 유효 단위는 다음이다.

```text
메시지 → Jev가 4분류와 confidence 반환 → 낮은 confidence는 Codex/Claude 또는 사람이 검토 → 확정된 분류만 기존 스킬 라우팅에 사용
```

이 구조에서는 Jev가 권한을 갖지 않는다. 파일 편집·외부 발신·명령 실행 권한은 기존 하네스와 에이전트 규칙에 남는다. 따라서 Jev는 에이전트를 대체하는 제품이 아니라, 에이전트 앞이나 사이에 넣는 **판단 전용 구성 요소**다.
